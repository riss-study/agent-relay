agent-relay 서버 설계와 배포 안내

team-relay 플러그인 0.10.2 를 그대로 쓰면서 중계 서버만 우리가 운영하기 위한 문서입니다. 지금 만들어진 서버가 어떻게 생겼고, 어디에 어떻게 올리며, 팀원은 무엇을 하면 되는지를 적었습니다.

작성일 2026-11-15. 기준 코드: 이 폴더의 server/relay.ts 828줄, server/frames.ts 147줄, server/relay.test.ts 327줄. 실행 환경 Node 24.15. 플러그인 계약은 docs/wire-protocol.md 에 있고 이 문서는 그 계약을 다시 적지 않습니다.

1한눈에 보기

팀원마다 Claude Code 세션이 하나씩 있고, 각 세션에는 배재원이 만든 team-relay 플러그인이 붙어 있습니다. 플러그인은 서버 주소 하나를 알고 그곳에 웹소켓으로 붙습니다. 지금까지는 그 주소가 배재원의 서버였고, 이제 우리 서버로 바꿉니다. 플러그인은 손대지 않습니다.

만들어진 것

  • 서버 한 파일. 참가, 메시지 전달과 보관, 답장 스레드, 무응답 통지, 방 담당, 기록 조회, 합의, 방 메모리, 방장 명령, 발신 상한, 관리자 HTTP(초대, 방장 지정, 토큰 폐기)가 들어 있습니다.
  • 저장은 sqlite 파일 하나(state.db)입니다. 서버를 재시작해도 멤버와 보관 메시지, 기록, 무응답 타이머가 남습니다.
  • 테스트 세 개가 실제 소켓으로 위 기능을 전부 돌립니다. npm test 로 2초 안에 끝납니다.
아직 안 한 것

다른 컴퓨터와 실제로 연결해 본 적이 없습니다. 검증은 이 Mac 안에서 플러그인 세션 하나와 스크립트 상대로만 했습니다. 외부망에 TLS 를 붙여 올린 적도 없습니다. 7절의 절차가 그 일을 위한 것입니다.

2전체 구조

그림에서 보라색 선은 웹소켓, 주황색 선은 세션 안에서 플러그인과 Claude Code 가 주고받는 표준 입출력입니다. 서버는 팀원 수와 상관없이 한 곳에 한 대만 있습니다.

플러그인은 서버 주소만 알고 서버 코드는 모릅니다. 그래서 서버는 팀원 PC 에 설치되지 않고 깃허브 배포도 필요 없습니다.

각 부분이 하는 일

부분어디에하는 일우리가 손대는가
Claude Code팀원 PC플러그인이 넣어 주는 <channel> 태그를 대화에 끼워 모델에게 보여 주고, 모델이 team_send 같은 도구를 부르면 플러그인에 넘긴다아니요
team-relay 플러그인팀원 PC서버에 웹소켓으로 붙어 요청을 보내고 푸시를 받는다. 30초마다 doctor 하트비트, 끊기면 재접속아니요. 배재원 저장소에서 설치
relay.ts서버 컴퓨터누가 어느 방에 있는지, 누구에게 전할지, 없으면 보관, 기한과 상한을 관리한다예. 이 폴더 전부
state.db서버 컴퓨터멤버와 토큰, 보관 메시지, 기록, 합의, 메모리를 담는 sqlite 파일백업만
Caddy서버 컴퓨터외부망일 때 인증서를 자동으로 받고 wss 를 평문 ws 로 바꿔 relay.ts 에 넘긴다설정 두 줄

3메시지가 오가는 순서

규영이 선혁에게 질문하고 답을 받는 가장 흔한 흐름입니다. 세션이 뜰 때의 선접속부터 적었습니다.

선혁 세션이 꺼져 있으면 서버가 message 를 보관함에 넣고 sent state:queued 로 답합니다. 선혁이 접속하면 그때 배달됩니다. 72시간이 지나면 버리고 규영에게 expired 를 보냅니다.

frames.ts

플러그인이 보내는 요청 19개, 서버 응답, 서버 푸시 5개의 모양을 TypeScript 인터페이스로 적어 둔 파일입니다. 서버는 응답을 만들 때 이 타입으로 검사받습니다. 런타임 코드가 없어서 플러그인을 포크하게 되면 그쪽에서도 같은 파일을 import 해 양쪽이 같은 모양을 쓰는지 컴파일로 확인할 수 있습니다.

relay.test.ts

환경변수로 기한을 수백 ms 로 줄인 뒤 서버를 빈 포트에 띄우고, 플러그인 흉내 클라이언트가 실제 웹소켓으로 요청을 보냅니다. 외부 테스트 도구 없이 node:test 만 씁니다.

  • 1단계: 참가, 발신, 답장, 무응답 통지, 보관과 재접속 배달, 퇴근과 출근, 담당 이전
  • 2단계: 기록 조회(상대, 스레드, 이전 장), 합의 제안과 확정, 방 메모리 쓰기와 제안, 방장 초대와 공지와 제외, 발신 상한
  • 3단계: 관리자 방장 지정과 토큰 폐기, 그리고 답을 기다리는 스레드가 든 state.db 로 서버를 자식 프로세스로 띄워 재시작 뒤 무응답 통지가 오는지

5설계

용어

말뜻
멤버토큰 하나로 식별되는 사람. 실제로는 그 사람의 PC 다. 여러 방에 속할 수 있다
라벨방 안에서 부르는 이름. 같은 사람이 방마다 다른 라벨을 가질 수 있다. 초대코드를 만들 때 정한다
방팀 단위. 메시지는 같은 방의 멤버끼리만 오간다. 방장이 있을 수도 없을 수도 있다
세션플러그인이 gateway:true 로 붙인 접속 하나. 한 사람이 Claude Code 를 여러 개 띄우면 세션도 여러 개다
담당한 멤버의 방 하나를 받는 세션은 하나뿐이다. 두 번째 세션은 시작만으로는 뺏지 못하고 room 요청으로 가져온다
스레드send 하나가 여는 1:1 대화. 답장은 스레드 id 로 상대를 찾는다

저장되는 것

sqlite 파일 하나에 표가 둘입니다. state 표는 행이 하나뿐이고 그 json 칸에 아래 전부가 들어갑니다. 바뀔 때마다 100ms 묶음으로 통째로 다시 씁니다. 지금 규모에서는 몇 KB 라 이 방식으로 충분하고, 멤버가 수백 명이 되면 표를 나눕니다. history 표는 보낸 메시지마다 한 줄씩 쌓이고 상한이 없습니다.

이름필드설명
membersid, token, rooms{방: 라벨}, away토큰이 신원이다. 폐기하면 통째로 지운다
roomsowner방장 멤버 id. 없으면 메모리 제안이 admin 으로 간다
invitesroom, name, owner, expires초대코드 1회용, 72시간. 코드가 키
threadsid, room, a, b, awaiting, noackAt, noticeawaiting 은 지금 답해야 할 쪽, noackAt 은 무응답 통지 시각. notice 는 공지라 답장 불가
queueto, from, room, push, deadline, frozenAt보관함. 상대가 퇴근 중이면 frozenAt 으로 기한을 멈춘다. 멤버당 50건
agreementsid, room, a, b, summary, details, state, expires합의. pending 이 72시간 지나면 expired
memorydescription, items[3], rev방 메모리. rev 가 다르면 쓰기 거절
proposalsid, room, from, text, expires방 메모리 수정 제안. 방장이 처리한다
history 표ts, room, sender, receiver, text, threadSQL 로 조회한다. 당사자만 볼 수 있고 라벨은 조회 때 붙인다

메모리에만 있는 것

열린 소켓과 세션, 어느 세션이 어느 방을 담당하는지, 무응답 타이머 객체, 최근 무응답 표시(30분), 상한 계산용 최근 1분 시각 목록입니다. 서버를 재시작하면 지워지지만 플러그인이 재접속하면서 세션과 담당은 다시 만들어지고, 무응답 타이머는 저장된 noackAt 으로 다시 걸립니다.

지켜지는 규칙

규칙동작
배달과 보관상대가 그 방을 담당하는 세션이 있고 퇴근 중이 아니면 바로 보낸다. 아니면 보관하고 queued 로 답한다
보관 기한72시간. 퇴근 중에는 멈춘다. 지나면 버리고 보낸 사람에게 expired
무응답expect:reply 로 보낸 뒤 15분 안에 reply 도 ack 도 없으면 보낸 사람에게 noack. 그 상대는 30분 동안 "최근 무응답"으로 표시돼 다음 발신에 note 가 붙는다
담당 이전다른 세션이 room 으로 가져가면 전 세션에 room_lost. 세션이 끊겨도 90초는 담당을 유지해 재접속하면 그대로 돌려준다
상한발신(send, reply, agree_propose, memory_propose) 분당 30건, 공지 분당 3건, 그 외 분당 120건
만료초대코드, 합의 제안, 메모리 제안 모두 72시간. 1분마다 치우고 제안자에게 system 메시지
방장초대, 제외, 공지, 메모리 쓰기는 방장만. 방장은 초대코드의 owner:true 나 관리자 HTTP 로 정한다
프로토콜 버전플러그인이 보내는 v 가 5 미만이면 plugin_outdated

6서버가 받는 요청 전부

플러그인이 보내는 프레임 type 과 서버 응답입니다. 필드 하나하나는 docs/wire-protocol.md 와 server/frames.ts 에 있습니다.

joinjoined초대코드로 참가. 토큰이 있으면 기존 신원에 방만 추가
sendsent새 스레드를 열어 상대에게 message 푸시. 상대가 나에게 물어 둔 스레드가 있으면 openThread 로 알림
replysent스레드로 답장. 무응답 타이머 해제

awayaway_ok퇴근이면 수신을 보관하고 기한을 멈춤. 출근이면 보관분 배달
roomroom_ok이 세션의 담당 방을 바꿈. 다른 세션 것은 뺏고 room_lost 를 보냄

doctordoctor30초 하트비트. 플러그인 자가 진단도 이걸 읽음
session_infosession_info_ok세션 이름 알림. 응답만 함
historyhistory당사자 기록 조회. peer, room, thread, before, limit(1에서 100)
agree_propose, agree_resolve, agree_listagree_ok, agree_resolved, agrees합의 제안, 확정과 거절, 목록. 확정되면 양쪽에 system 메시지
memory_get, memory_set, memory_propose, memory_resolvememory, memory_ok, memory_proposed, memory_resolved방 메모리 조회, 방장 쓰기, 멤버 제안, 방장 처리. 바뀌면 그 방 세션 전부에 room_memory 푸시
room_invite, room_kick, room_noticeroom_invite_ok, room_kick_ok, room_notice_ok방장 명령. 초대코드 발급, 멤버 제외, 전원 공지(kind:notice)

서버가 먼저 보내는 푸시

푸시언제
message팀원 메시지, 합의 제안, 메모리 제안, 공지, 시스템 알림. kind 로 구분하고 플러그인이 channel 태그로 넣는다
expired보관 기한이 지나 버렸을 때 보낸 사람에게
noack상대가 15분 안에 답도 ack 도 안 했을 때 보낸 사람에게

room_memory방 메모리가 바뀌었을 때 그 방의 모든 세션에
error reason:replaced_by_new_gateway같은 세션 id 로 새 소켓이 왔을 때 옛 소켓에. 플러그인은 재접속하지 않는다
error reason:revoked관리자가 토큰을 폐기했을 때. 플러그인은 알림을 띄우고 재접속을 멈춘다

관리자 HTTP

전부 POST 이고 JSON 본문과 authorization: Bearer 토큰 헤더가 필요합니다. ADMIN_TOKEN 이 비어 있으면 전부 401 입니다.

경로본문하는 일
/admin/inviteroom, name, owner?초대코드 발급. 방장이 없는 방의 첫 사람은 이걸로 들어온다
/admin/ownerroom, name그 방의 방장을 그 라벨의 멤버로 바꾼다
/admin/revokeroom, name그 멤버를 모든 방에서 지우고 열린 세션에 revoked 를 보내 끊는다

7배포 절차

역할이 둘입니다. 서버 관리자 한 사람이 서버를 올리고 초대코드를 나눠 주고, 팀원은 각자 플러그인을 설치해 참가합니다. 깃허브에 무엇을 올릴 필요는 없습니다. 플러그인은 배재원 저장소에서 설치되고 서버는 서버 컴퓨터에만 있으면 됩니다.

7.1 서버를 어디에 둘지 정한다

경우조건주소필요한 것
같은 사무실 LAN팀원 PC 가 전부 같은 네트워크. 재택은 VPN 으로 들어온다ws://서버IP:8765서버 PC 에서 RELAY_HOST=0.0.0.0, 방화벽 8765 허용
외부망집이나 외부에서도 바로 붙는다wss://relay.example.com공개 IP 가 있는 서버, 도메인, Caddy
평문 포트는 밖에 열지 않는다

토큰과 대화 내용이 지나가므로 외부망에서는 반드시 wss 입니다. relay.ts 는 기본으로 127.0.0.1 에만 묶여서 Caddy 를 거치지 않으면 밖에서 닿지 않습니다. LAN 에서 0.0.0.0 으로 여는 것은 사내망을 믿는다는 전제입니다.

7.2 서버 컴퓨터 준비

  1. Node 24 이상을 설치합니다. 이 서버는 Node 가 .ts 를 바로 실행하는 기능과 내장 sqlite 를 쓰므로 22 이하에서는 뜨지 않습니다. node -v 로 확인합니다.
  2. 이 폴더를 서버 컴퓨터에 복사합니다. node_modules 와 state.db 는 빼고 복사합니다. 사내 깃허브에 비공개 저장소로 두고 git clone 하는 편이 나중에 고칠 때 편합니다.
  3. 의존성을 설치하고 테스트를 한 번 돌립니다. 
    cd agent-relay
npm install
npm test        # pass 3 이면 된다
  4. 관리자 토큰을 만듭니다. 길고 무작위면 됩니다. 
    openssl rand -hex 24

7.3 실행

한 번 띄워 보는 명령입니다. 상시 실행은 7.4 에서 합니다.

# LAN 인 경우
RELAY_HOST=0.0.0.0 ADMIN_TOKEN=아까만든토큰 npm start

# 외부망인 경우 (Caddy 가 앞에 있으므로 기본 127.0.0.1 그대로)
ADMIN_TOKEN=아까만든토큰 npm start

뜨면 표준 오류에 한 줄이 나옵니다.

relay: ws://0.0.0.0:8765/ws (state /…/agent-relay/state.db)

환경변수

이름기본값뜻
PORT8765듣는 포트
RELAY_HOST127.0.0.1바인드 주소. LAN 평문이면 0.0.0.0
ADMIN_TOKEN(없음)관리자 HTTP 토큰. 없으면 관리자 기능 전부 거절
RELAY_STATEstate.dbsqlite 파일 경로
RELAY_INSTRUCTIONSserver/instructions.md규약 본문 파일
RELAY_QUEUE_TTL_MS, RELAY_NOACK_MS, RELAY_HOLD_GRACE_MS, RELAY_SEND_PER_MIN, RELAY_NOTICE_PER_MIN72시간, 15분, 90초, 30, 3기한과 상한. 테스트가 줄여 쓰고 운영에서는 손대지 않는다

7.4 상시 실행

Linux 서버면 systemd 유닛 하나로 부팅 때 뜨고 죽으면 다시 뜹니다. 토큰은 유닛 파일 대신 환경 파일에 두고 권한을 600 으로 합니다.

# /etc/agent-relay.env  (chmod 600)
ADMIN_TOKEN=아까만든토큰
RELAY_HOST=127.0.0.1

# /etc/systemd/system/agent-relay.service
[Unit]
Description=agent-relay
After=network.target

[Service]
User=relay
WorkingDirectory=/opt/agent-relay
EnvironmentFile=/etc/agent-relay.env
ExecStart=/usr/bin/node server/relay.ts
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target

# 적용
sudo systemctl daemon-reload
sudo systemctl enable --now agent-relay
journalctl -u agent-relay -f      # 로그

macOS 에 둔다면 launchd 의 LaunchDaemon 으로 같은 일을 합니다. ProgramArguments 에 node 와 relay.ts 경로, EnvironmentVariables 에 토큰, KeepAlive 를 true 로 둡니다.

7.5 외부망이면 Caddy

Caddy 는 도메인만 적으면 인증서를 자동으로 받고 갱신합니다. 80 과 443 포트가 밖에서 닿아야 합니다.

# /etc/caddy/Caddyfile
relay.example.com {
    reverse_proxy 127.0.0.1:8765
}

이 설정이면 /ws 와 /admin/* 이 둘 다 같은 도메인으로 나갑니다. 관리자 경로는 토큰이 지키지만 토큰이 짧으면 위험하니 7.2 처럼 무작위로 만듭니다. 다른 프록시(nginx 등)를 쓴다면 웹소켓 업그레이드를 켜고 유휴 끊김 시간을 플러그인 하트비트 30초보다 길게 둡니다.

7.6 초대코드 발급

방 하나에 사람마다 코드를 하나씩 만듭니다. 첫 사람에게 owner:true 를 주면 그 사람이 방장이 되고, 그 뒤 사람들은 방장이 자기 세션 안에서 초대 명령으로 직접 코드를 만들어 줄 수도 있습니다.

curl -X POST -H "authorization: Bearer $ADMIN_TOKEN" \
  -d '{"room":"web3","name":"규영","owner":true}' https://relay.example.com/admin/invite
# {"code":"TR-3F2A-9C1B","room":"web3","name":"규영"}

curl -X POST -H "authorization: Bearer $ADMIN_TOKEN" \
  -d '{"room":"web3","name":"선혁"}' https://relay.example.com/admin/invite

코드는 1회용이고 72시간 뒤 사라집니다. 코드와 함께 서버 주소를 전달합니다. LAN 이면 curl 의 주소도 http://서버IP:8765 입니다.

7.7 팀원이 할 일

  1. Claude Code 에 team-relay 플러그인 0.10.2 를 설치합니다. 지금까지 배재원 서버를 쓰던 사람은 이미 설치돼 있으니 건너뜁니다.
  2. Claude Code 세션에서 참가 명령에 서버 주소와 받은 코드를 줍니다. 주소는 스킴까지 적습니다. 플러그인은 스킴이 없으면 ws:// 를 붙이므로 외부망에서 빠뜨리면 평문으로 붙으려다 실패합니다. 
    /team-relay:join wss://relay.example.com TR-3F2A-9C1B
# LAN 이면
/team-relay:join ws://192.168.0.10:8765 TR-3F2A-9C1B
    참가하면 플러그인이 토큰을 자기 설정 파일에 저장합니다. 이 토큰이 그 사람의 신원이라 다른 PC 로 옮기지 않습니다.
  3. 메시지를 받으려면 팀 세션으로 띄웁니다. 플러그인이 제공하는 claude-team 실행이 TEAM_RELAY_GATEWAY=1 을 켜 줍니다. 팀 세션이 아닌 세션은 보내기만 되고 받지 못합니다.
  4. 세션 안에서 team_doctor 를 불러 연결과 설정을 확인합니다. 연결이 "연결됨" 이고 방에 자기 라벨이 보이면 끝입니다.

7.8 둘이서 확인

두 PC 에서 각각 팀 세션을 띄운 뒤 한쪽에서 상대 라벨로 질문을 보냅니다. 상대 세션 화면에 channel 알림이 뜨고, 답하면 보낸 쪽에 답이 돌아오면 됩니다. 한쪽을 끄고 보내면 queued 로 답이 오고, 다시 켜면 그때 배달되는 것까지 보면 보관함도 확인한 것입니다.

8운영

규약 본문 바꾸기

server/instructions.md 를 고치면 끝입니다. 파일 수정 시각이 rev 가 되어 다음에 뜨는 세션부터 새 본문을 받고, 플러그인은 rev 가 바뀌면 캐시를 갱신합니다. 서버 재시작도 필요 없습니다.

방장 바꾸기와 사람 내보내기

curl -X POST -H "authorization: Bearer $ADMIN_TOKEN" -d '{"room":"web3","name":"선혁"}' https://relay.example.com/admin/owner
curl -X POST -H "authorization: Bearer $ADMIN_TOKEN" -d '{"room":"web3","name":"규영"}' https://relay.example.com/admin/revoke

폐기된 사람의 세션에는 "[팀 연결 종료] 관리자가 이 계정의 접속을 차단했습니다" 알림이 뜨고 재접속이 멈춥니다. 다시 쓰려면 새 초대코드로 참가합니다. 방 하나에서만 빼고 싶으면 방장이 세션 안에서 제외 명령을 씁니다.

백업

state.db 와 같이 생기는 state.db-wal, state.db-shm 을 함께 복사하거나, 서버가 떠 있는 채로 아래를 돌립니다.

sqlite3 state.db ".backup /backup/state-$(date +%F).db"

토큰이 들어 있으니 백업 파일도 권한 600 으로 둡니다.

서버 코드를 고쳤을 때

  1. 고친 뒤 npm run check 와 npm test 를 돌립니다.
  2. 서버 컴퓨터에서 코드를 받고 systemctl restart agent-relay 합니다. state.db 는 그대로 남습니다.
  3. 재시작 동안 플러그인은 연결 실패를 보고 1초부터 두 배씩 늘려 30초까지 재접속을 시도합니다. 몇 초 안에 다시 붙고 담당도 돌아옵니다. 그 사이 온 메시지는 보낸 쪽이 실패 응답을 받으니 다시 보내면 됩니다.

플러그인이 새 버전이 되면

배재원이 플러그인을 올려 프로토콜 번호가 6 이 되면 플러그인이 보내는 필드와 읽는 필드가 바뀔 수 있습니다. 그때는 새 태그의 플러그인 소스에서 docs/wire-protocol.md 를 다시 뽑고 서버를 맞춥니다. 팀원이 자동 갱신을 받기 전에 서버를 먼저 맞추는 것이 순서입니다. 갱신을 미루고 싶으면 0.10.2 태그를 사내 깃허브에 포크해 두고 거기서 설치하게 하면 됩니다. 코드를 고치지 않는 단순 복사입니다.
